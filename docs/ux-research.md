# 使用者研究：誰會用這個網頁

2026-10-22。這份是從軟體工程角度推導的需求分析（persona、情境、任務、非功能需求），還沒有做真人訪談。依據來自同類產品的公開設計（見 [design-research.md](./design-research.md)）、環境部 AQI 健康建議的分眾方式，以及這個專案過去的產品決策（[DECISIONS.md](../DECISIONS.md)）。

## 1. Persona

| # | Persona | 情境 | 想知道什麼 | 裝置 | 對設計的意義 |
|---|---|---|---|---|---|
| P1 | **戶外運動的上班族**（慢跑、騎車、通勤），30 歲，住新北 | 早上 6:30 出門前、下班要不要去河濱跑步 | 「我這區現在能不能跑？」 | 手機、單手、可能在戶外強光下 | 一打開就要看到自己測站的數字與一句建議；不能每次都重新選站 |
| P2 | **敏感族群的照顧者**：家有氣喘兒或長輩的家長，40 歲，住臺中 | 送小孩上學前、週末安排出遊 | 「敏感族群要不要戴口罩、減少活動？」 | 手機，一天會看好幾次 | 敏感族群建議要和一般民眾分開寫；數字不能只靠顏色表達；過期資料不能被誤認成現在 |
| P3 | **戶外活動負責人**：體育老師、營隊或活動企劃 | 決定今天的體育課或戶外活動要不要移到室內 | 官方類別名稱、學校附近測站，必要時比較幾個鄰近測站 | 桌機或筆電為主，手機為輔 | 需要官方用語（如「對敏感族群不健康」）、發布時間與官方連結；地圖和列表要能快速比較 |
| P4 | **作品集訪客**：招募者、工程師、環境資料愛好者，從 GitHub 點進來 | 花 1–3 分鐘評估作者的能力 | 「這個產品做得好不好？資料可不可信？」 | 桌機為主 | 第一屏就要看得出專業水準；地圖、深色模式與資料時效處理是展示重點；README 要說清楚架構 |

## 2. 前三項任務（依頻率與重要性排序）

1. **查看我的測站現在的空氣品質，並決定要不要調整活動**（P1、P2、P3）。
   成功標準：再次造訪時 0 次點擊就看到結果；第一次造訪時，輸入 2 個字＋1 次點選就看到結果；5 秒內看懂數字、類別與建議。
2. **判斷資料是不是現在的**（所有人）。
   成功標準：時效永遠在頁首可見；過期時有一個明確的警示，數字變灰，並暫停建議。
3. **看全台或鄰近地區哪裡比較差、哪裡比較好**（P3、P4）。
   成功標準：地圖上的數字一眼可讀；列表可以依縣市篩選、依 AQI 排序；點選後立刻更新上方卡片。

次要任務：了解 AQI 分級（色階條、圖例）、確認資料來源與授權（頁尾）、看原始碼（頁尾連結）。

## 3. 非功能需求

| 類別 | 需求 | 如何落實與驗證 |
|---|---|---|
| 可信度 | 不用過舊、範例資料或時間異常的資料提供「現在」的結論 | 前端依發布時間分三段（≤ 90 分鐘即時、≤ 6 小時稍舊、≤ 24 小時過舊），超過 24 小時或時間異常才不提供建議（2026-10-23 起，取代原本的 3 小時門檻）；資料時間永遠顯示在 AQI 旁 |
| 效能 | 4G 手機 LCP < 2.5 s，CLS < 0.1 | 地圖延遲載入；固定高度容器避免版面跳動；Lighthouse 行動版效能 ≥ 90 |
| 無障礙 | WCAG 2.1 AA：對比 ≥ 4.5:1、觸控目標 ≥ 44 px、可完全用鍵盤操作、不只用顏色傳達資訊 | 色票對比有計算紀錄；地圖有對等的列表；Lighthouse 無障礙 ≥ 90 |
| 安全 | MOENV API key 永遠不進前端 bundle 或 repo | 只在 Actions 端抓資料；部署前掃描 `dist/`；前端只讀同站的靜態 JSON |
| 隱私 | 不要求定位、不追蹤使用者、不放第三方分析工具 | 選過的測站只存在使用者瀏覽器的 localStorage；唯一的第三方請求是 OSM 地圖圖磚 |
| 可用性 | 上游失敗時，線上不能變成空白頁 | fail-closed 部署（失敗就保留上一版）；前端有載入、錯誤、空資料、過期四種狀態 |
| 維運 | 不產生 bot commit，部署可以重現 | 單一 workflow 從 main 建置；資料只存在 Pages 產物中 |
| 在地化 | 繁體中文、Asia/Taipei 時區、「台／臺」都搜得到 | 時間一律用 `Intl` 加上 `timeZone: 'Asia/Taipei'` 格式化；搜尋時把「台」正規化成「臺」 |

## 4. 裝置評估

- **整體流量**：StatCounter 2026 年 9 月的台灣網頁流量，手機約 58%、桌面約 39%、平板約 3%（[來源](https://gs.statcounter.com/platform-market-share/desktop-mobile-tablet/taiwan)，以瀏覽量計算）。
- **產品本身**：「出門前快速看一眼」的任務（P1、P2）幾乎都發生在手機上。同類產品（環境即時通、IQAir、AirVisual）也以 App 和手機為主要入口，所以手機比例應該高於整體的 58%。
- **作品集情境**：P4 從 GitHub 點進來，多數用桌機。他們的第一印象會直接影響作品集的評價。

**結論：兩邊都重要。** 手機是產品的主力裝置，要做到精緻：單欄、大數字、44 px 觸控目標、地圖和列表用分頁切換。桌面是作品集的門面，也要好看：地圖和列表並排、卡片寬度受控、有留白。兩邊都會在 390 px 與 1440 px 實際截圖檢查。

## 5. 自我審查（2026-10-22，production build）

| 項目 | 結果 | 依據 |
|---|---|---|
| 視覺層級：5 秒內看懂 | ✅ | 首屏依序是標題、搜尋框加六都快速選站、全台三個數字加分布條；選站後的順序是 AQI 色塊、站名、類別、發布時間 |
| WCAG AA 對比 | ✅ | 中性 token 在淺色與深色模式下對所有背景都 ≥ 4.5:1。淺色的 `faint` 原本只有 3.5:1，已調整為 `100 108 121`。AQI 色塊上的文字 4.8–11:1 |
| 觸控目標 ≥ 44 px | ✅ | 390 px 下以腳本列出所有小於 44 px 的互動元素，只剩 sr-only 的「跳到主要內容」；地圖縮放鈕放大為 44 px。地圖上的數字標記例外，列表提供同等功能 |
| 載入、空資料、錯誤、過期 | ✅ | `?demo=loading`、`?demo=empty`、`?demo=error` 和舊快取都實際截圖檢查過；修正空資料時的錯誤文案 |
| 深淺色 | ✅ | 跟隨系統，可手動切換；head 內聯腳本在首次繪製前套用主題，不會閃白；地圖圖磚同步反轉 |
| 沒有版面跳動 | ✅ | CLS：行動版 0.004、桌面 0.007；地圖容器高度固定 |
| 鍵盤與螢幕閱讀器 | ✅ | combobox 支援上下鍵、Enter、Esc；地圖標記可聚焦；地圖有對等的列表；狀態訊息用 `role=status` |
| 地圖標記可讀 | ✅ | 依螢幕像素做碰撞避讓（`src/lib/pinLayout.ts`，有單元測試）：優先顯示所選測站，再來是有效資料、AQI 較高者；會重疊的改成同色小圓點，放大後展開成數字。1440 px：30 個數字＋54 個圓點；390 px：24＋60 |
| 無水平捲動 | ✅ | 375 與 390 px 下 `scrollWidth === clientWidth` |

**Lighthouse 13.5.0**（本機 `vite preview`，數字依序為 performance／accessibility／best practices／SEO）：

- **行動版**：99／100／96／100，LCP 1.8 s，CLS 0.004
- **桌面版**：99／100／100／100，LCP 0.9 s，CLS 0.007

行動版 best practices 96 分的唯一扣分項是「OSM 圖磚在高 DPI 螢幕上解析度偏低」。改用 retina 圖磚會讓圖磚請求變成 4 倍，違反 OSM 的使用政策，所以保留現狀。

過程中修掉的問題：
- 嘗試延遲載入地圖，結果手機 LCP 變差（LCP 元素正是圖磚），所以改回同步載入，並對圖磚伺服器加 preconnect。
- 地圖數字標記在手機上重疊，提高精簡模式的縮放門檻。
- 標出主要污染物所在的卡片。
- 首屏加入六都快速選站與分布條，第一次造訪 1 次點擊就能看到結果。
